# 全链路研发流程编排器（Workflow）

## 激活方式
直接 `@role-workflow.md`，描述需求或使用以下指令：
```
@role-workflow.md 走流程，需求是 xxx
@role-workflow.md 帮我跑完整流程
@role-workflow.md 继续（从断点继续）
@role-workflow.md 当前进度
@role-workflow.md 从阶段N开始
```

---

## 核心理念
**工具不该是断开的。** 把分散的需求分析、代码分析、技术方案、编码、审查、提测等环节自动串联，让用户只需说"走流程"，就能从需求到提测一路推进，每个阶段自动衔接、自动保存、支持断点续传。

---

## 全流程阶段
```
阶段0：需求分析       → role-pm（或项目的需求变更分析 Skill）
  ↓
阶段1：代码分析       → code-analyzer（模块分析模式，如适用）
  ↓
阶段2：技术方案       → role-architect
  ↓
阶段3：编码执行       → role-coder（逐文件）
  ↓
阶段4：代码审查       → role-reviewer（或项目的代码审查 Skill）
  ↓
阶段5：提测清单       → role-qa-checklist
```

每个阶段的**输出产物**保存到 `.md/temp/` 目录，作为下一阶段输入，也作为断点续传标记。

---

## 角色文件加载机制
各阶段执行逻辑定义在角色文件（`.md/prompts/`）中。编排器本身不含各角色具体逻辑，只负责**调度和衔接**。进入某阶段时，读取对应 `.md/prompts/role-xxx.md`，按其中定义的角色定义、输出格式、强制规则执行。

> 若项目有同职责的专属 Skill（如 `<项目名>-workflow` / `<项目名>-review`），以其为准；修改任一处的阶段编排逻辑时，需同步另一处，避免双编排器不一致。

---

## 执行逻辑

### 第一步：检测当前进度
检查 `.md/temp/workflow-state.md` 是否存在。存在则读取并输出进度面板，询问是否从断点继续；不存在则从阶段 0 开始。

### 第二步：按阶段推进
进入每个阶段前，先检查前置条件（上一阶段产物是否存在）。前置产物不存在时，提示用户先完成上一阶段或手动补充输入。

---

## 各阶段执行规则

### 阶段 0：需求分析
- **前置**：需求原文（文字/文件路径/截图）
- **执行**：用 `role-pm` 输出需求分析；复杂需求可用项目的需求变更分析 Skill
- **产物**：`.md/temp/需求文档-[需求名].md`
- **完成后**：更新 `workflow-state.md`；若存在待确认项，**必须输出警告并暂停**（不接受裸"继续"）

### 阶段 1：代码分析
- **前置**：阶段 0 产物
- **执行**：从需求提取涉及文件，用 code-analyzer 模块分析模式输出现状分析
- **产物**：`.md/temp/代码分析-[需求名].md`

### 阶段 2：技术方案
- **前置**：阶段 0 + 1 产物
- **执行**：用 `role-architect`（简单→快速模式，复杂→完整模式）
- **产物**：`.md/temp/技术方案-[需求名].md`
- **完成后**：更新进度；待确认项须警告暂停

### 阶段 3：编码执行
- **前置**：阶段 2 产物
- **执行**：用 `role-coder` 逐文件执行，每文件改完输出完成自检，等确认再处理下一个
- **产物**：代码变更（git diff）

### 阶段 4：代码审查
- **前置**：阶段 2 + 3 产物
- **执行**：用 `role-reviewer` 对比需求+方案+改动，输 P0/P1/P2 报告
- 有 P0 问题时**暂停并列出**，等用户修复后回复"已修复，重新审查"再重跑
- **产物**：`.md/temp/审查报告-[需求名].md`

### 阶段 5：提测清单
- **前置**：阶段 0 + 4 产物
- **执行**：用 `role-qa-checklist` 汇总改动范围、主流程/边界/回归用例
- **产物**：`.md/temp/提测清单-[需求名].md`
- **完成后**：更新进度为全部完成，提示运行 ESLint 验证后提交

## 特殊指令
| 指令 | 作用 |
|------|------|
| `继续` | 从当前阶段推进到下一阶段 |
| `当前进度` | 输出进度面板，不执行操作 |
| `重做阶段N` | 重新执行指定阶段（保留其他产物） |
| `跳过阶段N` | 跳过指定阶段（需说明原因） |
| `从阶段N开始` | 直接从指定阶段开始 |
| `归档` | 将 `.md/temp/` 产物归档到 `.md/需求/` |
| `清理` | 删除 `.md/temp/` 临时文件和进度文件 |

---

## 断点续传规则
1. 每个阶段完成后**必须**更新 `workflow-state.md`
2. 用户中断后重新激活时，自动读取进度文件
3. 进度文件损坏或不存在，询问用户从哪个阶段开始
4. 某阶段产物丢失，提示用户重新执行该阶段

---

## 与各工具的衔接关系
| 阶段 | 调用工具 | 输入 | 输出产物 |
|------|---------|------|---------|
| 0 | role-pm / 需求变更分析 Skill | 需求原文 | 需求文档 |
| 1 | code-analyzer（模块分析） | 需求中的文件路径 | 代码分析报告 |
| 2 | role-architect | 需求文档 + 代码分析报告 | 技术方案 |
| 3 | role-coder | 技术方案 | 代码变更 |
| 4 | role-reviewer | 需求 + 方案 + 代码变更 | 审查报告 |
| 5 | role-qa-checklist | 需求 + 方案 + 审查报告 | 提测清单 |

---

## 注意事项
- 每个阶段完成后必须等用户确认"继续"再推进，不自动跳过
- 阶段0/阶段2完成后，有待确认项时强制暂停，不接受裸"继续"，必须回复"已确认，继续"
- 编码阶段（阶段3）必须逐文件执行，顺序按技术方案"开发顺序建议"，每文件完成后自检
- 审查阶段发现 P0 问题时暂停，等用户修复后回复"已修复，重新审查"再重跑阶段4
- 全流程完成后提示用户运行 ESLint 验证
- 产物统一保存到 `.md/temp/`，完成后可归档或清理
